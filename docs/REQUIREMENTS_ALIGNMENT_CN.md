# 13 步工作流：需求对齐与减少后期修改

本文档从全栈技术视角评估：**13 步契约优先工作流能否尽可能对齐需求、减少后期修改**，并给出可落地的加强点。

---

## 结论（简短回答）

**能。** 当前设计已经通过「契约优先 + 单源真相 + 分散测试 + 漂移检查」在很大程度上有助于对齐需求、减少后期返工。若再补上**需求追溯**和**验收标准与测试的显式绑定**，可以进一步逼近「尽可能对齐、减少后期修改」的目标。

---

## 已有优势：为什么能对齐需求、减少返工

| 机制 | 作用 |
|------|------|
| **契约优先（Spec 前置）** | 先定 proposal → spec，再 design → tasks；实现以 spec 为准，避免「先写代码再补文档」导致的需求漂移。 |
| **单源真相（spec.md）** | Mock 数据、骨架返回、种子数据、契约测试、Drift 检查都引用 spec 的 JSON/结构；前后端共用同一份契约，减少理解偏差。 |
| **显式非目标与边界（Proposal）** | Non-Goals、Edge Cases & Risks 必须写清，缩小范围、减少「以为要做/没做」的争议。 |
| **Step 3 验证门** | 提案逻辑经用户验证后再写 Spec，避免错误理解直接进入契约。 |
| **Design 依赖 Spec** | design.md 以 spec 为输入，路由/服务/表与端点一一对应，设计不会脱离契约。 |
| **任务依赖链** | tasks 依赖 design + spec，任务中的路径、类名、表名要求「具体化」，避免泛泛而谈导致实现偏离。 |
| **分散测试（即做即测）** | Task 4.2 / 5.2 / 5.4 / 5.6 等紧跟实现，问题早暴露；不是堆到 Step 11 才测，减少后期大改。 |
| **Step 12 Drift 检查** | 代码与 spec 的偏差被量化（&lt;1%），强制对齐契约。 |
| **StandardResp + 错误码** | 统一响应格式与错误码（infrastructure.md），前后端和测试对「成功/失败」的语义一致，减少联调阶段的误解。 |

综合来看：**需求 → 契约 → 设计 → 任务 → 实现 → 测试** 是一条清晰链路，且有多处「以 spec 为准」的约束，所以能显著提高需求对齐度并降低后期修改成本。

---

## 潜在缺口：哪里还可能造成后期修改

| 缺口 | 说明 |
|------|------|
| **Proposal → Spec 无显式追溯** | 用户故事与验收标准（AC）若没有在 spec 里显式对应到端点/行为，容易出现「AC 写了但 spec 漏了」或「spec 多了但没对应 AC」的偏差。 |
| **验收标准 → 测试无显式绑定** | AC 在 proposal 里，测试在 design/tasks 里，若没有「每条 AC 对应哪种测试」的约定，容易漏测或测非所需。 |
| **Spec 完整性依赖人工** | 虽有 Validation Checklist，但若不在工作流里强制「写 spec 时逐条勾选 + 评审」，仍可能漏字段、漏错误码、漏分页等，后期才发现。 |
| **非功能需求未成体系** | 性能、限流、安全等若只散落在 Edge Cases 或 infrastructure，没有在 proposal/spec 里占位，容易被遗忘，后期再补成本高。 |
| **契约变更与版本** | 需求变更导致 spec 变更时，对「兼容性、版本、回归范围」的指引不够显式，可能带来后期兼容性返工。 |

---

## 建议改进（可落地）

1. **在 spec 中增加「需求追溯」**  
   - 在 spec 模板中增加可选小节：**Requirements Traceability**。  
   - 每个端点（或接口组）注明对应的 **User Story / 验收标准**（如 Story 1 / AC-1.1）。  
   - 作用：Proposal ↔ Spec 可对照，评审和变更时一眼看出「有没有漏、有没有多」。

2. **在 proposal 中提示与 spec 的衔接**  
   - 在 User Stories 或验收标准处增加一句：**「后续在 spec.md 中需为每个验收标准建立对应的 API 或行为说明（可追溯）。」**  
   - 作用：写 proposal 时就形成「AC 将来要进 spec」的习惯，减少漏写。

3. **在 design 的验证计划中显式绑定 AC 与测试**  
   - 在 Verification Plan 中增加：**「验收标准覆盖：每个 proposal 中的验收标准应至少被以下之一覆盖：单元测试、集成/契约测试、E2E/前端验证。」**  
   - 并在 design 模板中留一个简表（可选）：AC 编号 → 覆盖方式（单元/集成/E2E）。  
   - 作用：测试范围与需求显式对齐，减少「做了功能但没测到 AC」或「测了很多但没覆盖关键 AC」。

4. **在任务/工作流说明中强调「先勾 Spec 再开发」**（已落实）  
   - 在 `openspec/schemas/workflow/schema.yaml` 的 spec 生成说明中已增加：写 spec 时必须完成 **Validation Checklist**，在进入 design（Step 5）前逐条勾选并在评审时确认。  
   - 作用：把「Spec 完整性」变成流程动作，而不是事后检查。

5. **非功能与契约变更（可选增强）**（已落实）  
   - 在 `openspec/schemas/workflow/templates/proposal.md` 的 Impact 下已增加 **5.3 Non-Functional Requirements（可选）**：Performance、Rate limiting/Security、Compatibility 占位。  
   - 若项目有 API 版本策略，可在 spec 或 infrastructure 中简短说明「契约变更时版本与兼容性策略」。  
   - 作用：非功能与契约演进有固定入口，减少后期补课。

---

## 小结

- **能否尽可能对齐需求、减少后期修改？** 能；当前 13 步工作流已经通过契约优先、单源真相、分散测试和 Drift 检查做了大部分工作。  
- **还能做什么？** 补上 **Proposal ↔ Spec 追溯**、**验收标准与测试的显式绑定**、以及 **Spec 完整性在流程中的强制勾选**，可以进一步减少遗漏和偏差，把「尽可能」再推高一步。  
- 上述改进已部分纳入本仓库的 **proposal / spec / design 模板** 与 **docs/REQUIREMENTS_ALIGNMENT.md**，可按项目需要选用或裁剪。
